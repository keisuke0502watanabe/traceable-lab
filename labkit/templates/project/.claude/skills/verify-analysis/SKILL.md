# 解析を検証する

検証は二段に分ける。**機械で分かること**は `labkit check` に任せ、**数値の正しさ**は生データからの検算で確かめる。

## 0. 機械の点検

```bash
labkit check            # 読むだけ。reports/check_report.md
```

入力ファイルの書き換え、台帳の値の変更（質量の修正・status: bad）、置き換え済みの版を used のまま、
上流の誤り、作成後に変わったスクリプト、0 バイトのファイル、検証の記録が無い used を拾う。最初に結果をユーザーに見せる。

## 1. 点検メモを作る

```bash
labkit audit <名前>     # notes/audit-<名前>_<日付>.md
```

## 2. 検算する（ここが本体）

- **点検中は何も直さない。** DATA・analyses・スクリプトは読むだけ。直すのはユーザーと順番を決めてから
- 範囲が広ければ領域に分け、サブエージェントに並行で任せてよい（それぞれ読むだけ、検算スクリプトは scratch/ に）
- **コードを読むだけで終わらせない。** 生データ（`labkit.ledger` の `resolve`）から、解析とは別に書いたコードで
  同じ数値を出し直し、`out/` の CSV と突き合わせる。一致した件数と、食い違った測定 ID を数える
- 誤りの型を順に疑う: 並び順、名前の読み取り、補間で埋めた値、決め打ちの定数、片側だけの条件、表の結合のずれ、
  単位、時刻の基準、途中で止めた測定、テストが「古いツールと同じ」を見ているだけで正しさを見ていない
- 判定（結晶化した／しない、相の帰属など）は、独立な指標を二つ三つ測って突き合わせる
  （例: 保持中の発熱と、続く昇温の融解熱）
- 合成データ（答えが分かっているもの）を同じ手順に通すと、方法の癖が数で分かる

## 3. 分けて書く

点検メモに **誤り（再現した）／要注意／問題なし／見ていないもの／直す順の案** を書く。
誤りには「何本のうち何本に当たったか」と、`labkit downstream <ana_id|スクリプト>` で出した影響する解析を必ず添える。
「見ていないもの」を省かない。

## 4. 記録する

```bash
labkit verify <ana_id> --result ok|caution|error --method "<どう確かめたか>" --note "<一行>" --report notes/audit-…md
```

ギャラリーとビューアに「検証済み／要注意／誤りあり」の印が出る。誤りのある解析の下流は `labkit check` で要注意になる。

## 5. 直す（ユーザーが決めたあと）

1. ライブラリやスクリプトを直し、テストを足す（直す前に失敗し、直したあとに通るもの）
2. `labkit downstream <直したスクリプト>` の順に、新しい版を `supersedes` つきで作り直す
3. 古い版は `status: rejected` にして、notes.md に理由と点検メモの場所を書く
4. `labkit refresh` → `labkit check` で、誤りと要注意が減ったことを確かめる
5. 日誌に一行
