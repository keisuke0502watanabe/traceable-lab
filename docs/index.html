論文の図から、生データまで辿れる研究フォルダ

DSC、XRD、SAXS の測定は増え続けます。半年後に「この図はどの測定から、どの条件で描いたのか」と聞かれたとき、すぐ答えられる形でフォルダを組むための教材です。実際に一年近く運用して、測定約 1,900 件と解析約 400 件を回した仕組みを、一般化して紹介します。

論文・スライドの図Fig. 5（脚注に ana_id）
→

→
manifest.jsoninputs: [meas_id, …]

この教材の中心はこの鎖です。どの段も機械で読める形で残すので、逆向き（この測定を使った解析はどれか）にも辿れます。

00

この教材について

対象は、実験データを自分で解析して論文や発表にまとめる大学院生・研究者です。

仕組みの半分は、ただのフォルダ構成と CSV です。どのエディタやプログラムでも同じように使えます。残りの半分は、AI のコーディング助手（ここでは Claude Code）に作業を任せるときの約束ごとです。人に引き継ぐときにもそのまま役に立ちます。各節に次の印を付けました。

誰でも使える Claude があると楽になる やってはいけないこと

例に出す試料名・ID・数値は説明用に作ったものです。実際のデータは含みません。

01

五つの約束 誰でも使える

仕組みの細部は変えてかまいません。この五つだけは守ります。

  1. 生データは凍結する測定ファイルは置いたら動かさない、名前も変えない。分類したくなったら台帳の列（タグ・状態・メモ）を書き換えます。フォルダを動かすと、過去の解析が指していたパスが壊れます。
  2. 一行が一測定の台帳を持つ測定ごとに一行の ledger.csv。日付・試料・質量・熱履歴・ファイルのパスが並びます。台帳はスクリプトが生データから作り直せる「生成物」です。
  3. 一つの問いに一つの解析フォルダ「Ta が誘導時間をどう決めるか」のような問いごとに analyses/ana-日付-名前/ を作り、入力の測定 ID・パラメータ・結果・図を中に閉じ込めます。
  4. 消さずに、状態で残す失敗した解析も消しません。status: rejected にして残し、やり直しは新しいフォルダを作って前の ID を supersedes に書きます。捨てた理由は、あとで一番役に立つ記録です。
  5. 生成物は手で直さない台帳・ギャラリー・スライド・論文の図は、スクリプトから作り直せるようにしておきます。直すのは元（スクリプトや原稿のテキスト）で、出力された .pptx や .png は直接いじりません。
02

フォルダの地図 誰でも使える

まず、研究のファイル全体を内容別に分けます。クラウドの種類や年度で分けると、同じものが何か所にも散らばります。番号は並び順を固定するためです。

~/Research と ~/Projects
~/Research/
  0-受け皿/        置き場所に迷ったもの。週に一度振り分ける
  1-執筆/          原稿・投稿論文・査読。業績/ は自分の論文の最終版
  2-発表/          発表・講義。1-conference/年/発表名/
  3-文献/          文献 PDF（文献管理ソフトから参照する）
  4-データ/        実験のプロジェクト。ここに台帳と解析がある（次の節）
  5-ラボ・教育/    研究室・学生・実習
  6-事務・研究費/  申請書・執行書類
  9-アーカイブ/    古いもの。中は整理しない
  README.md        ← 地図の正本。置き場所とルールはここだけに書く
  MOVES.md         ← 動かしたときの「元の場所 → 新しい場所」

~/Projects/        ← プログラムだけ。git で管理する
  tag-analysis/    計算ライブラリと解析スクリプト

README.md を地図にする

どこに何を置くかを一枚に書き、ルールを変えたらここを直します。人に聞かれたらこのファイルを渡します。

MOVES.md に移動を記録する

古いパスが書かれたメモやスクリプトを見つけたとき、この表で新しい場所が分かります。日時・元・先の三列で十分です。

やってはいけないこと過去の発表のパワーポイントを新しい発表フォルダにコピーしない。使った正本の場所を ref.md にメモします。重複ファイルの一番の原因でした。ファイルは消さず、不要なら _重複/ かアーカイブへ移します。
03

一つのプロジェクトの中 誰でも使える

実験のプロジェクト（例：4-データ/fat-crystal-project/）は、次の形にそろえます。赤が凍結する場所、緑がスクリプトで作り直す生成物です。

プロジェクトの雛形
fat-crystal-project/
  DATA/               凍結層。新しい測定は装置/日付で足すだけ
    dsc/  xrd/  saxs-beamline/
  ledger.csv          測定台帳。一行 = 一測定（labkit ledger が作る）
  ledger_gaps.csv     機械で埋まらなかった行の一覧（手で埋める宿題）
  analyses/           一問い = 一フォルダ。平らに並べる。消さない
    ana-20250914-ppp-avrami-ta45/
      manifest.json  notes.md  out/
  analyses_index.csv  全 manifest の一覧
  reports/            人に見せるもの
    figure_gallery.html   全解析の図のサムネイル一覧
    analyses_viewer.html  解析の系譜をたどるビューア
    index.csv             レポート ↔ ana_id の対応表
    oral-conf-2025/  poster-conf-2025/
  Documents/
    manuscript-<テーマ>/    論文ごとの作業フォルダ（11 節）
  notes/              日付ごとの短い日誌と、申し送り（HANDOFF）
  scratch/            試行錯誤。月に一度空にしてよい
  tools/              台帳・ギャラリーを作るこのプロジェクト専用のスクリプト

計算そのもの（ピーク検出、Avrami の当てはめ、XRD のピークフィット）は、プロジェクトの外の ~/Projects にライブラリとして置きます。プロジェクトの tools/ には、そのプロジェクトのファイル構成に依存するものだけを置きます。

04

測定台帳 ledger.csv 誰でも使える

エクセルで手書きする台帳ではなく、生データのファイルから毎回作り直す台帳です。

DSC のテキスト出力には、測定日時・試料名・質量・温度プログラムが書いてあります。XRD やビームラインのデータにも、ヘッダや温度ログがあります。これを読んで一行にまとめるスクリプト（labkit ledger。自分の装置の形式は reader を一つ書いて足す）があれば、測定が増えても台帳は数秒で作り直せます。

二種類の ID

meas_id は測定

ファイルの中身（測定日時・走査番号）から決めます。ファイル名から決めると、名前を変えたときに ID が変わってしまいます。

dsc-20250414-095225
xrd-20250613-143901
sr-202507-PPP-3_75-57_48

ana_id は解析

日付と短い名前。測定と解析は多対多で、対応は解析側の manifest が持ちます。

ana-20250914-ppp-avrami-ta45
ana-20250916-c8tag-t-ind-sensitivity

列の例

meas_idinstrsamplemass_mgthermal_historyTa_Cpathstatustagsnote
dsc-20250429-132754dscC8TAG4.1225→50@10 > hold50/5min > 50→-20@15 > hold-20/30min > -20→20@5-20DATA/dsc/2025-04/…txtokta-scan
dsc-20250429-154927dscC8TAG4.2425→50@10 > hold50/5min > 50→-25@15 > hold-25/30min > -25→20@5-25DATA/dsc/2025-04/…txtbadパンの蓋が浮いた
xrd-20250613-143901xrdPPPhold80 > to48@15 > hold48/30min > to79@248DATA/xrd/2025-06/…rasokiso
  • 固定する列は三つ：meas_id・path・thermal_history。ほかの列は増やしても並べ替えてもかまいません。
  • 手で書く列（status・tags・note）は、作り直しても消えないようにスクリプトで引き継ぎます。
  • 熱履歴は短い記法で一行に。A→B@rate が昇降温、holdT/Nmin が等温保持。これで「Ta が 30–50 °C の PPP の DSC」を一行で選べます。
  • 同じ測定のコピー（バックアップ、zip の展開など）は行を持たせず、正とした行の duplicates 列にパスを並べます。
  • 機械で埋まらなかった行は ledger_gaps.csv に出します。ここが「人が実験ノートを見て埋める」宿題の一覧になります。
Python から使う
from labkit import ledger
L = ledger.load()                     # cwd から上へ ledger.csv を探す
rows = L.select(instr="dsc", sample="PPP", Ta_C=(30, 50))
for r in rows:
    print(r["meas_id"], r["thermal_history"], L.resolve(r))
05

解析フォルダ analyses/ 誰でも使える

解析を始めるときにフォルダを作り、終わるときに状態を書きます。中身は三つだけです。

manifest.json

問い・入力の meas_id・手順・パラメータ・結果・状態・系譜。機械が読む部分。

notes.md と out/

notes.md は「問い／分かったこと／次」の三段。out/ に図・表・CSV。

analyses/ana-20250914-ppp-avrami-ta45/manifest.json
{
  "ana_id": "ana-20250914-ppp-avrami-ta45",
  "question": "PPP の Ta = 45 °C 付近で Avrami 指数 n は Ta にどう依存するか",
  "inputs": ["dsc-20250429-132754", "dsc-20250429-154927"],
  "procedure": "tools/avrami.py",
  "params": { "t0Mode": "induction", "inductionFrac": 0.05, "Xrange": [0.2, 0.8] },
  "results": { "n": 2.8, "n_ci95": [2.6, 3.0] },
  "status": "used",             // used / tried / rejected
  "supersedes": "ana-20250913-ppp-avrami-ta45",
  "based_on": [],                // 別の解析の出力を入力にしたとき
  "inputs_sha1": { … },  "code": { … },  // 作った時点の指紋（07 節の検証で使う）
  "checks": []                   // 検証の記録
}
いつもの流れ
from labkit import ledger, analysis
L = ledger.load()
rows = L.select(instr="dsc", sample="PPP", Ta_C=(40, 50))
A = analysis.new(L, "ppp-avrami-ta45", question="…", inputs=rows,
                 procedure="tools/avrami.py", params={"t0Mode": "induction"})
# … 計算。図は A.out("xt_curve.png") に保存する
A.finish(results={"n": 2.8}, status="used")
根拠を辿る・一覧を作る
labkit trace ana-20250914-ppp-avrami-ta45   # 図 → 測定 → 生ファイル
labkit index                                # analyses_index.csv を作り直す

既にある解析を後から登録する

この仕組みを入れる前に作ったまとめ（生データのフォルダの中にある古いレポートなど）は動かしません。analyses/ に manifest と notes だけを置き、external_dir で実体を指します。これで古い成果も同じ鎖に入ります。

規約も解析として残す「誘導時間の閾値を 1 % ではなく 5 % にする」のような決めごとは、その根拠になった比較を一つの解析フォルダにして、README に「決めた日付と ana_id」を書きます。数か月後に「なぜ 5 % なのか」と聞かれても、その解析を開けば答えられます。
06

DSC・XRD・SAXS のコード 誰でも使える

測定の種類が増えると、似た計算があちこちのスクリプトにコピーされ、少しずつ食い違っていきます。そこで役割を三層に分けました。

層置き場所中身
ライブラリ~/Projects/…/<研究室のライブラリ>/数値を出す関数はここにしか置かない。
dsc.parse（装置ごとのテキスト → 共通の行）、dsc.peaks（外挿オンセット・ΔH）、dsc.avrami、xrd.parse（.ras / 1D .dat / .xrdml）、xrd.peakfit（pseudo-Voigt、d・q、Scherrer）、xrd.phase（長面間隔とサブセル線から α / β′ / β）、kinetics（DSC と XRD 共通の Avrami）
解析スクリプトskills/…/scripts/ライブラリを呼んで図や表を作る。一本のスクリプトが一つの解析フォルダに書く
判断と規約Markdownベースラインの取り方、t₀ の定義、相の判定の閾値。コードではなく文章で、日付と根拠の ana_id つきで残す

古いツールの結果を「全桁一致」で移す

以前使っていた解析ツール（ブラウザで動く DSC/XRD アナライザなど）からライブラリへ関数を移すときは、古いツールが保存していた結果を新しい関数で再計算し、一致することをテストにしました。移植で数値が変わっていないことを、後から誰でも確かめられます。

回帰テスト
python3 tests/test_dsc_regression.py    # 保存済みのピーク 6 件を全桁で再現するか
python3 tests/test_xrd_regression.py    # 保存済みのピーク 73 本を再現するか
python3 tests/test_transient.py         # 合成データ（n = 2 と分かっている曲線）でのテスト

合成データで方法の癖を測る

答えが分かっている合成曲線（例：n = 2 の Avrami 曲線にノイズと装置の過渡応答を足したもの）を、実データと同じ手順に通します。「この規約だと n が 1.4 まで下がって見える」と分かれば、報告するときに n を規約と一緒に書く理由になります。

装置ごとの注意を README に熱履歴の記法、装置の温度ログの読み方（ログの一行目が系列の始まりか終わりか）、試料温度とプログラム温度の差など、一度調べて分かったことは README に一文で残します。同じ調査を二度しないためです。
07

検証する 誰でも使える Claude

解析が数百になると、小さなコードの誤りが下流の図や論文の数値にそのまま流れます。

回帰テストは「古いツールと同じ答えを出すか」を見ているだけで、答えが正しいかは見ていません。そこで検証を二段に分けます。機械で分かることは毎回自動で点検し、数値の正しさは節目ごとに生データからの検算で確かめます。

1. 機械の点検（毎回）

解析フォルダを作るとき、manifest に三つの指紋を残しておきます。入力ファイルの sha1、そのときの台帳の値、スクリプトの sha1 です。labkit check はこれといまを比べるだけなので、数秒で終わり、何も変えません。

見つけるものよくある原因
生データが書き換わった・消えたDATA の中で上書き保存した、フォルダを動かした
0 バイトのファイル、台帳に入らなかったファイル書き出しや変換が途中で落ちた。黙って抜けるのがいちばん怖い
解析のあとで台帳の値が変わった質量の打ち間違いを直した、測定を bad にした。古い値で計算した解析が残っている
解析のあとでスクリプトが直された同じ結果になるかは、作り直さないと分からない
置き換え済みの版が used のまま論文やスライドが古い版を引用している
上流に誤り・置き換えがある別の解析の出力を入力にしている（based_on）
点検（読むだけ）
labkit check            # reports/check_report.md に 誤り・要注意・参考 で書く
labkit check --strict   # 誤りがあれば終了コード 1（投稿前の確認に）

2. 数値の検算（節目ごと）

論文に出す前や、おかしな値に気づいたときに行います。

  1. 点検中は何も直さない。読むだけにして、直すのは順番を決めてから別の作業として行います。
  2. 範囲を領域に分ける。台帳、ビューア、速度論、相の判定、論文の図、のように分けます。Claude なら領域ごとにサブエージェントへ並行で任せられます。
  3. コードを読むだけで終わらせない。生データから、解析とは別に書いたコードで同じ数値を出し直し、出力の CSV と突き合わせます。何本のうち何本が食い違ったかを数えます。
  4. 誤りの型を順に疑う。並び順の取り違え、ファイル名の読み取り、補間で埋めた値、決め打ちの定数、片側だけの条件、表の結合のずれ、時刻の基準、途中で止めた測定。
  5. 判定は独立な指標で確かめる。「結晶化しなかった」という判定なら、保持中の発熱と、続く昇温の融解熱の両方を見ます。
  6. 四つに分けて書く。誤り（再現した）／要注意／問題なし／見ていないもの。「見ていないもの」を省かないことが、次の点検の出発点になります。
点検メモと記録
labkit audit segments     # notes/audit-segments_日付.md（誤り／要注意／問題なし／見ていない／直す順）
labkit verify ana-20250914-ppp-ta-scan --result error \
    --method "生データから段の境界を出し直した" --note "途中で止めたランで境界が前にずれる"
labkit downstream tools/segments.py   # 直したら作り直す解析を、上流から順に

記録した結果は、ギャラリーとビューアに「検証済み」「要注意」「誤りあり」の印で出ます。誤りのある解析を元にした下流の解析は、labkit check で要注意として挙がります。直したら新しい版を supersedes つきで作り、古い版は rejected にして理由を残します。

ビューアや解析に使ったコードの正しさを検証して。何も直さずに、生データから別のコードで出し直して比べて、誤り・要注意・問題なし・見ていないもの に分けて notes/audit に書いて。
実例この運用で点検したところ、DSC の測定を段（昇温・保持・冷却）に切る関数が、予定の時間を比例配分していたため、途中で止めた測定でだけ境界をずらしていました。当たったのは数百本中の十数本です。テストは古いツールと同じ答えを出すので通っていました。生データからの検算でしか見つからない種類の誤りです。
08

図ギャラリーと解析ビューア 誰でも使える Claude

解析が数百になると、「あの図どれだっけ」が一番の時間泥棒になります。全解析の out/*.png を一枚の HTML に並べる figure_gallery.html と、解析の系譜を木で見る analyses_viewer.html を、スクリプトで生成します。

試料
状態

ギャラリーの模型（中の図と ID は説明用）。本物は試料・状態・主題・月・語句で絞り込み、日付・解析・試料でまとめ、クリックで拡大、解析 ID から解析ビューアへ飛べます。

  • 解析ビューアは「試料 → 主題 → 系統（-2、-3 の版と supersedes の連なり）→ 版」の木。manifest と notes.md を読むだけなので、解析フォルダは一切動かしません。
  • スライドや Word に貼る PNG は tools/pdf_to_png.py で作り、出どころを三か所に残します：ファイル名 <ana_id>__元の名前.png、図の下の小さな脚注、PNG のメタデータ。貼った図から解析に戻れます。
解析を足したら毎回
labkit refresh      # 台帳 → 解析の一覧 → ギャラリーとビューア → 点検の要約
ルールにして自動化する「解析を足したら最後に必ずギャラリーも更新する」を README と Claude のメモリの両方に書きました。人が忘れても、Claude が解析の最後に labkit refresh を回します。
09

日誌と申し送り 誰でも使える Claude

解析フォルダは「何をしたか」を残します。その日なぜそれをしたか、何を捨てたかは日誌に書きます。

ファイル書くこと

スライドとポスター Claude があると楽になる

発表資料も「元から作り直せる生成物」として扱います。スライドの文章と図の指定は一つのテキスト（例：content.py）に書き、ビルドスクリプトが HTML・PPTX・PDF を出します。

  handover.md               §0 現状 / §1 どこに何 / §2 ビルド / §3 構成
  src/
    content.py              スライドの本文と図の指定（直すのはここだけ）
    build_html.py           → HTML。PPTX と PDF も同じ元から
    fig_*.py                スライド専用の図。データは ana_id の out/ から読む
    facts.md                スライドに出す数値の正本
    notation.md             記号の取り決め（ΔT の基準など）
  talk-v17.html  talk-v17.pptx  talk-v17.pdf
  旧_v13-v16/

facts.md と notation.md

数値と記号の定義を一か所に固定します。AI に書かせると、版を重ねるうちに数値や定義がいつの間にか変わることがあります。撤回した値もここに「撤回」と書きます。

版番号と持ち時間

出すたびに v を一つ上げ、古い版はフォルダに退避。「いまの構成で 18:05 / 15:00 枠」のように時間も申し送りに書きます。

やってはいけないこと.pptx や .html を直接編集しない（次のビルドで消えます）。多形などの色の割り当てを途中で変えない（例：α 青・β′ 赤・β 緑。論文・ポスター・スライドで共通）。

ポスターも同じ作りです。A0 の HTML をビルドし、「ポスターに使った図だけの一覧」を別に生成します。質疑で「この点は何本の測定から？」と聞かれたときの棚卸し表も、同じフォルダに作っておきます。

口頭発表のスライドの続き。handover.md の §0 を読んでから始めて。スライド 26 の図は B 案を本編、A 案を予備に。content.py を直して v18 をビルドして。

論文の作業フォルダ 誰でも使える Claude

論文一本につき一つ、Documents/manuscript-<テーマ>/ を作ります。データと同じプロジェクトの中に置くので、図のスクリプトは解析フォルダを相対パスで読めます。

Claude との分担 Claude があると楽になる

ここまでの仕組みは、人だけでも回せます。AI のコーディング助手を使うと、台帳やギャラリーのスクリプトを書く、毎回の再生成、日誌、申し送りといった手間の大部分を任せられます。そのための置き方を四つ紹介します。

1. 入口を一つにする

Claude Code は起動時に ~/.claude/CLAUDE.md を読みます。ここには地図の場所だけを書き、中身は ~/Research/README.md に一本化します。二か所に書くと、片方だけ古くなります。

~/.claude/CLAUDE.md
# フォルダの地図
研究・教育・事務のファイルは ~/Research にまとめてある。
置き場所とルールは ~/Research/README.md を読むこと（地図の正本）。
移動の履歴は ~/Research/MOVES.md。プログラムは ~/Projects。

2. 繰り返す作業は skill にする

「DSC のフォルダを渡されたら、台帳を作り、ピークを検出し、Ta と多形の関係をまとめ、HTML のレポートとスライドを出す」のような一連の手順を、skill（手順書とスクリプトの束）にまとめます。次からは「このフォルダの DSC をまとめて」で同じ品質の結果が出ます。判断の規約も skill の Markdown に書くので、別の日・別のチャットでも同じ基準で解析されます。

3. 短いメモリに「いつも」を書く

「解析したら毎回ギャラリーを作り直す」のような、毎回の指示を一行のメモリにします。言い忘れても守られます。

4. 一つの作業に一つのチャット

解析・スライド・論文を別々のチャット（セッション）で進め、受け渡しは request／handback のファイルで行います。会話が長くなったら HANDOFF を書かせて新しいチャットに移ります。

任せること人が決めること
台帳・ギャラリー・ビューアのスクリプトを書いて回す何を問うか（解析フォルダの question）
解析フォルダを作り、manifest と notes を埋める規約（閾値、基準、記号）と、その採否
日誌・HANDOFF・PROGRESS の更新どの図を論文やスライドに使うか
スライドや図のビルド、版の管理数値が物理的に正しいか、文献と合うか
Claude に渡す禁止事項DATA/ に触らない、analyses/ を消さない、ファイルを動かすときは提案して承認をもらってから動かし MOVES.md に書く、.pptx を直接編集しない。これをプロジェクトの README に書いておくと、別のチャットでも同じように守られます。

頼み方の例

PPP の DSC で Ta = 40–50 °C のものを台帳から選んで、Avrami の n と誘導時間を Ta に対して並べて。解析フォルダを作って、終わったらギャラリーも更新して。
この解析は t₀ の取り方を間違えていたので rejected にして、理由を notes.md に書いて。直した版を supersedes つきで新しく作って。
論文の Fig. 5 の根拠を辿って。どの測定を使って、そのうち status が bad のものは入っていないか確認して。
今日の作業を notes/ の日誌にまとめて、明日の自分向けに HANDOFF を書いて。

明日から始める 誰でも使える

全部を一度にそろえる必要はありません。効果の大きい順に並べました。

  1. README.md を一枚書く。フォルダの地図と、DATA に触らないという約束だけでよい。
  2. 生データを DATA/ に集めて凍結する。今後は足すだけ。
  3. 台帳を作る。最初は手書きの CSV でも、meas_id, path, thermal_history, status, note の五列で始められます。慣れたらスクリプトで生成に切り替えます。
  4. 次の解析から analyses/ana-日付-名前/ を作る。manifest は question と inputs だけでも価値があります。
  5. 日誌を一日三行書く。回した ana_id と、捨てた方向。
  6. 解析が 20 を超えたら、図ギャラリーを作る。
  7. 発表や論文の図には ana_id を脚注で入れる。これで鎖がつながります。
  8. 論文に出す前に一度、検算する。点検メモを作り、結果を解析に記録します。
雛形を作るコマンド
mkdir -p my-project/{DATA,analyses,notes,scratch,tools,reports,Documents}
printf 'meas_id,instr,date,sample,thermal_history,path,status,tags,note\n' > my-project/ledger.csv
printf '# my-project\n\n## 二つの禁止\n1. DATA/ に触らない\n2. analyses/ を消さない\n' > my-project/README.md

入れ方と試し方
